# Phase 0 — spike results

Status: **complete on Linux** (2026-11-26). Base: rustudio 0.5.2 source tree.
The remaining Phase 0 items are the clean VM / network-namespace run and the
visual review, both deferred for now (the clean-HOME, no-Studio run is done
natively instead as a partial stand-in).

- a baseplate and SpawnLocation;
- a wall with a Decal using `rbxassetid://900000001`, whose bytes are in
  `cache/assets/900000001_vlatest.bin`;
- a Speaker with a looping Sound using `rbxassetid://900000002`, same cache
  layout, `Playing = true`;
- `ReplicatedStorage/Animations/Wave`, a KeyframeSequence with poses for R15
  (`UpperTorso → RightUpperArm`) and R6 (`Torso → Right Arm`) that waves the

  it with `Humanoid:LoadAnimation` (the current form).

Both rig variants are generated by `game/fixtures/phase0/make_fixture.py`.

## Results

`scripts/phase0-smoke.sh` passes three runs, all headless:

| Run | Rig | Content | Result |
|---|---|---|---|
| Launcher, R15 | R15 | engine-local Studio content (Vinegar) | pass |
| Engine, R6 | R6 | engine-local Studio content | pass |
| Launcher, R15 | R15 | clean `HOME` + `RUSTUDIO_STUDIO_DIR=/nonexistent` (blocky fallback) | pass |

Each run asserts, from the fixture's Output lines:

- `PROBE texture=Success sound=Success` — both bundled assets resolve from
  `cache/`, never the network (the smoke also asserts no
  `Downloaded asset 90000000N` lines);
- `PROBE track length=1.000 playing=true` — the in-place KeyframeSequence has
  a real length and plays;
- `PROBE joint=RightShoulder moved=25 distinct=25` (R15) and
  `joint=Right Shoulder moved=20 distinct=21` (R6) — `Motor6D.Transform`
  actually changes;
- `PROBE sound playing=true length=2.00` — the sound decodes and starts;
- `PROBE done`, and the launcher propagates exit code 0.

The clean-HOME run created only the GPU driver's shader caches and an empty
`~/.cache/rustudio/crash`; the game itself wrote nothing outside the bundle.

As a native stand-in for the network-namespace gate, the clean-HOME/no-Studio
run was repeated under `strace -f -e trace=connect,sendto`: it made **no
AF_INET/AF_INET6 connections** (the only `connect` calls were two to the
local Wayland socket, from the windowing stack), and the fixture completed.

The launcher was exercised from the repository root, so its bundle
resolution-from-executable-path works; its log records the env it applied
(each variable skipped if the developer had set it).

## Finding: `Sound.Playing = true` never started (upstream bug, fixed)

A Sound saved with `Playing = true` did not play at the start of a Play
session, on either side, even though `Playing` read true and the asset
decoded. `TimeLength` was right; `IsPlaying` stayed false.

Cause: `start_autoplay_sounds`
(`crates/rustudio-player/src/play_game.rs`). In `play.rs` `start_play`, the
player switches the shown DataModel to the client (`show_play_side(Side::Client)`)
*before* calling it. The scan therefore walked the **client** document and
passed its client refs as `server` refs to `sound_command`;
`client_of(client_ref)` returned `None`, so the server runtime was marked
playing with a ref that did not belong to it, and the client was never marked
at all. (`Run` mode has no client document in front, so it was unaffected.)

Fix: `start_autoplay_sounds` now swaps the server document to the front for
the scan and restores the previous view after it (`server_front` /
`shown_front`, both already used elsewhere in the same file).

Regression test:
`play::autoplay_sound_tests::saved_playing_sound_autoplays_on_both_sides`
(`crates/rustudio-player/src/play.rs`). Verified to fail without the fix
(`Sound.IsPlaying is not true` on the server side) and pass with it; the full
`rustudio-player` suite still passes (50 + 1 tests).

This is upstreamable as-is: a three-call change plus a test, no API change.
It is a candidate for an upstream PR (FORK-PLAN §2.1, §13.5) and should be
dropped from the fork once merged. Until then the working tree carries it;
it is not listed in the §11 patch stack because it is a bug fix, not fork
behaviour.

## Upstream churn surface

Upstream is under active development, so this matters more than the code:
what would a future upstream update actually touch?

Only **two upstream files** are changed, and both are in `rustudio-player`:

- `crates/rustudio-player/src/play_game.rs` — the autoplay fix above
  (swap the server document in for the scan). Should be an upstream PR
  immediately; drop the local copy once it lands.
- `crates/rustudio-player/src/play.rs` — the regression test (one
  `#[cfg(test)]` module at the end of the file).

`.gitignore` gained two downstream build paths; that is a one-line conflict
surface at worst. The root `Cargo.toml` is untouched: `game/` is its own
workspace (`game/Cargo.toml`), which Phase 0 validated by building the
launcher with `--manifest-path game/Cargo.toml` while the upstream workspace
builds independently.

Everything else is in new paths that do not exist upstream, so a rebase
cannot conflict with it:

- `game/launcher/` — no rustudio dependencies; only the bundle format and
  the environment-variable contract, both ours to change.
- `game/fixtures/phase0/` — a place file and a Roblox-API-only LocalScript;
  the player CLI and the Roblox API are the only surfaces.
- `scripts/phase0-*.sh` — calls `cargo build -p rustudio-player`, the launcher,
  and the player's harness flags (`--headless`, `--seconds`, `--log`,
  `--fail-on-error`).

If upstream renames an environment variable, a harness flag, or the player
crate, the fix is in our files, not a merge conflict. If upstream rewrites
`start_autoplay_sounds` itself, re-derive the three-call patch against the
new code and re-run the regression test (FORK-PLAN §2.9). The fixture and
launcher stay unchanged.
